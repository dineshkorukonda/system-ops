# Staged upgrades and rollback

The native updater no longer resets the live checkout, clears stashes or removes its dist directory. scripts/deploy.sh invokes the Linux/root-only release helper. It fetches main without modifying working files, extracts a versioned stage as the service account, installs dependencies, runs isolated tests, builds assets and runs production smoke checks before activation. Tests use a separate data directory, never the operator's monitoring database.

Validated releases link the shared root .env/data directory. A systemd drop-in runs current/src/start.js; current is switched with an atomic symlink rename. The helper restarts the service and gates on readiness plus authenticated persistence health for durable releases. If readiness fails it restores the prior pointer and restarts the previous process. A flushed journal records the previous path before activation; the next invocation recovers an interrupted upgrade. Old assets and data are kept intact. A release revision file prevents version checks from reporting the original checkout's stale commit after deployment.

This targets Ubuntu/systemd and assumes the service account already has access to the repository and required Node/npm binaries. A custom port requires READINESS_URL. The helper requires a readable .env with APP_PASSWORD for the persistence gate. SQLite version 1 is additive; future incompatible schema rollback requires a data backup. The helper refuses targets outside the release root and does not delete release directories or shared data. Old stages may be manually cleaned after verifying rollback/backup needs.

CI runs Linux pointer/build-failure/path-boundary tests and a real production-process fixture for successful activation, injected readiness failure, previous-process restoration, journal recovery and shared-data/asset preservation. Windows skips the three Linux symlink tests. No live server or native systemd service has been upgraded by this agent; actual installer/account/sudoers and host-specific unit configuration remain deployment verification work. Container deployments continue to use immutable images and persistent volumes rather than this native helper.

## Dashboard updater launch

The dashboard invokes the exact permitted sudo command, using noninteractive sudo and the deploy wrapper background mode. The wrapper starts system-ops-update.service outside the dashboard service control group, so restarting the dashboard cannot kill the updater. The worker appends to shared update.log and atomically records an ops-readable update-result.json after readiness/rollback. A short launch grace period avoids reporting failure before systemd has created the unit. Root checkout and active release paths are distinct, so updates remain supported after the first staged activation. Docker/Windows installs are reported as unsupported for dashboard self-update.

Existing broken dashboard installations need a one-time SSH update: from the root checkout run `sudo bash scripts/deploy.sh`. After the repaired version is installed, dashboard updates use the independent worker. This bypasses the old API launcher without resetting the checkout or deleting assets. Native sudoers/systemd behavior still needs verification on the target server; no live host was modified here.
